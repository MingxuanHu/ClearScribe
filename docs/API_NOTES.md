# API decisions

Reviewed against official documentation on **2026-10-23**. Account entitlement and successful real audio transcription were not tested; these are documentation-backed adapters with offline mock validation.

- [Dedicated Realtime transcription guide](https://developers.openai.com/api/docs/guides/realtime-transcription): fixed server WebSocket URL `wss://api.openai.com/v1/realtime?intent=transcription`; no model in URL. Send `session.update` with `type: transcription`, nested `audio.input`, PCM at 24000 Hz, transcription model, `turn_detection: null`. Wait for `session.updated` confirming the requested type/model.
- The same guide confirms `gpt-live-transcribe` continuous deltas and commit finalization. It does not support server/semantic VAD. `gpt-transcribe` in this workflow starts recognition after a committed turn; it is labeled accordingly. Both use `languages` rather than singular `language`, plus prompt/keywords. Delay is configured only for the live adapter.
- [Transcription overview](https://developers.openai.com/api/docs/guides/transcription) confirms the workflow distinction. No file transcription, assistant, response creation or output audio API is used.
- [Deprecations](https://developers.openai.com/api/docs/deprecations): reviewed before selection; older Whisper/4o transcription models are excluded. `gpt-realtime-whisper` is not added: the guide does not recommend it for new integrations and a third adapter is unnecessary.
- [Models list reference](https://developers.openai.com/api/reference/resources/models/methods/list): `/v1/models` provides basic IDs/ownership/creation and shutdown metadata, not a realtime capability matrix. This implementation uses exact IDs intersected with the maintained capabilities. Announced shutdown rows are conservatively excluded.
- [Client events reference](https://developers.openai.com/api/reference/resources/realtime/client-events) and [server events](https://developers.openai.com/api/reference/resources/realtime/server-events) document append, commit/committed and `conversation.item.input_audio_transcription.delta`, `.completed`, `.failed`. The model guide explicitly warns completion order across items is not guaranteed. The server binds commit acknowledgements FIFO, reconciles text by item ID and application sequence, and drops retired socket generations. Model context validation is conservatively restricted locally; upstream rejection remains possible.
- Some generic schema descriptions still associate delay with an older model. The dedicated guide explicitly configures it for `gpt-live-transcribe`; that guide is followed. SDK enums are not used as evidence for model capabilities. The guide does not publish an exact prompt-length number; the application's 400-character cap is a local conservative bound, not a claimed API limit.
- [General Realtime lifecycle guide](https://developers.openai.com/api/docs/guides/realtime-conversations) documents a 60-minute ceiling for general Realtime sessions; the dedicated transcription guide does not establish a separate lifetime promise for these two models. The application requests a new transcription session after 50 minutes (or earlier from `expires_at` if present), with a 45-second deadline and explicit failure/gap behavior. This policy needs real long-call validation.

The API supplies no word timestamps, speaker labels or confidence for the live model. Sample-clock segment starts are application approximations. Stop pads extremely short nonempty turns to 120 ms before committing; silence alone never creates an item. Reconnect/replay is intentionally absent. A failed switch stops; it never silently substitutes an assistant or batch model.
